Orchestration: what it is and why bother

  • What it is: the layer that decides when multiple agents run, how they hand off, and how their outputs are checked. Without it, "multi-agent" is a chain of prompts with no state, no audit, no owner.
  • Why not one megaprompt: specialization beats a generalist (planner ≠ risk reviewer ≠ implementer); each role gets its own inputs, outputs, and permissions; each role leaves a diffable artifact you can review after the fact.
  • Two flavors, both needed:
    • Agent orchestration — coordinates roles (who does the work).
    • Model orchestration — coordinates models within a role (which brain runs the work).
  • The cost you pay: coordination. The payoff: observability, least-privilege-per-job, safe autonomy, and an audit trail by construction.
  • Framing for the rest of the deck: the orchestrator is the platform, agents are contributors, and humans still own the outcome.

Orchestration patterns and how to pick one

Five patterns worth knowing:

PatternMechanismGood for
SequentialOutput of A → input of B, in a fixed orderPipelines: plan → verify → act
ConcurrentSame task fanned out to N agents; results aggregatedIndependent analyses, ensemble decisions
Group chatAgents talk in a shared thread coordinated by a managerMaker/checker, brainstorming with humans in-loop
HandoffEach agent decides whether to keep the task or transfer controlDynamic routing when the right expert isn't known
MagenticA manager builds and refines a ledger of subgoals as it goesOpen-ended tasks with no predetermined plan
  • Rule of thumb: sequential when order is fixed, concurrent when work is independent; reach for group-chat / handoff / Magentic only when the extra flexibility earns its complexity.
  • Durable default for "analyze → decide → act": sequential outer, concurrent inner — a.k.a. fan-out / fan-in with a deterministic merge step (not another LLM call).

Model orchestration with HydraFusion: many models per role (Preview)

  • What it is: picking or combining models within a single agent's turn — as opposed to routing between agent roles.
  • Why bother: no single model is best at everything. Routing recovers frontier quality without paying frontier price / latency on every call; ensembling can beat the best single model on hard tasks.
  • Common shapes:
    • Router — a lightweight classifier picks one model per request (cheap for easy tasks, capable for hard ones).
    • Ensemble / fusion — run several models in parallel and merge their candidates (voting, verifier-picks-best, or a fuser LLM that composes a final answer).
    • Escalation — try a cheap model first; escalate to a stronger one on low confidence or failed verification.
  • Relationship to agent orchestration: agent orchestration decides who does the work; model orchestration decides which brain that agent uses. Governance (plan, risk gate, permissions, audit trail) is agnostic to which model produced the output — that's what makes model swaps and A/B rollouts safe.
  • Example — Project HydraFusion: GitHub's approach ensembles several frontier models per Copilot request and uses a fuser to combine candidates; internal evals show quality above the best single model at controlled cost and latency.

Plan-first governance

  • Single, linkable task contract. Every agent run needs a stable, human-authored input it can be traced back to — not an ad-hoc prompt. Reproducibility, audit, and accountability all depend on this.
  • Structured, machine-checked plans. Force plans into a fixed schema (goal, scope, steps, risks, rollback) and validate before anything downstream trusts them. Structure is the substrate every later control reads.
  • Promote the plan template to a required check. A PR template is a suggestion; a required status check is a contract — and it prevents template drift over time. Read the PR body as data, never as executable string.
  • Anti-pattern avoided: "trust me" PRs where intent lives only in the diff.

In this repo: prepare uploads issue.md; spec_analyzer emits the plan JSON and jq validates it; open-agent-pr renders it into the PR body via plan-template.md; plan-gate.yml runs on every PR to main and fails if any required section is missing.

Autonomy, safety, and least privilege

  • Risk-based autonomy. Let a machine-readable risk signal drive routing; default to caution on unknown or malformed values. Low-risk work flows automatically; higher risk gets a human before merge.
  • Approval gates through the platform. Reuse the same environment-based gating you already trust for deployments — don't invent an agent-only approval story. Gate the act stage, not the think stage.
  • Least privilege, per job. Default to no permissions; grant write only to the specific job that needs it, and only at the stage where it needs it. "Think" agents read; "act" agents write, and only after approval.
  • Layered prompt-injection defenses. Assume any single layer will be bypassed: structural separation of untrusted content, read-only tool allowlists for planning agents, and output schema validation before trusting anything downstream.

In this repo: plan_merger normalizes risk and defaults to high; implement runs under environment: approval-required with if: risk != 'low'; the workflow header sets permissions: {} and each job opts in; copilot-json-task wraps issue text in <ISSUE> tags, restricts Copilot to view,glob,grep, and re-parses output with jq.

Takeaways

  • Orchestration is a workflow with state, not a chain of prompts.
  • Sequential outer, concurrent inner is a durable default for "analyze → decide → act."
  • Agent orchestration picks the role; model orchestration picks the brain. Governance covers both — the same plan, risk gate, and audit trail work regardless of which model produced the output.
  • Enforce the checklist through the platform — templates, required checks, environments, permissions — not through hope.
  • Agents change who performs work; humans still own the outcome.
