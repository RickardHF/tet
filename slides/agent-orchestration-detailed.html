What is AI agent orchestration?

Press ↓ for details

  • Orchestration is how multiple agents coordinate their work in a shared environment: when they run, how tasks are sequenced, and how outputs flow between steps.
  • Without orchestration you get "prompt-to-prompt daisy chains" — brittle, unobservable, and unowned.
  • With orchestration, agents become contributors to a system that has plans, checks, evidence, and reviewers.
  • In this repo, the orchestrator is GitHub Actions. The unit of work is a labeled issue. The output is a draft PR with a machine-checked plan.

Reference: Learn — Agent orchestration in GitHub workflows

Orchestration is the coordination layer: when agents run, how work is sequenced, and how outputs move between stages. In this repository GitHub Actions is the orchestrator, a labeled issue is the unit of work, and a draft pull request is the result.

Why not a single agent?

  • Specialization: one agent per role beats one megaprompt (planner ≠ risk reviewer ≠ implementer).
  • Scalability & maintainability: agents can be added, tested, and swapped independently.
  • Safety: separating "think" from "act" lets you apply least privilege per job.
  • Observability: each agent leaves an artifact you can inspect after the fact.
  • Trade-off: coordination cost. Orchestration is what makes that cost worth paying.
Explain why role specialization improves maintainability, safety, and observability. The cost is coordination; orchestration is the mechanism that makes that cost worthwhile.

Which patterns show up in the workflow?

Two patterns, layered:

1. Sequential (outer)

prepare → planning stage → plan_merger → implement*. The workflow is a deterministic pipeline; each stage depends on the previous one.

2. Concurrent / fan-out–fan-in (inner)

spec_analyzer and risk_reviewer run in parallel from the same input and are joined by plan_merger.

This is the fan-out / fan-in pattern: a widely recommended best practice for composing analyze / review / merge phases without letting them collide.

References: Workflow — plan-implement.yml · Learn — Agent orchestration in GitHub workflows

The outer workflow is sequential. Inside the planning stage, two independent analyses run concurrently and join through a deterministic merge step.

Role specialization: one agent, one job

Press ↓ for details

  • Give each agent a narrow role with typed inputs and outputs so it can be tested, swapped, or upgraded in isolation.
  • Separate "think" agents (analyze, review) from "act" agents (implement, deploy) — different permissions, different failure modes.
  • Explicit handoffs between roles make the system observable: every stage leaves an artifact you can diff against later.
  • The alternative — one megaprompt doing everything — hides reasoning and makes least-privilege impossible.

In this repo: spec_analyzer emits {goal, scope, steps, mitigations, rollback}; risk_reviewer emits {risk}; implementer runs only after the merged plan and only under approval.

References: Workflow — plan-implement.yml · Learn — Scale and failure recovery · Article — What is AI agent orchestration?

Each agent has one narrow job and a typed handoff. This makes roles independently testable, separates think permissions from act permissions, and leaves observable artifacts.

Good practice #1: a single, linkable task contract

  • Every agent run needs a stable, human-authored input it can be traced back to — not an ad-hoc chat prompt.
  • The task contract has to be reproducible: same input, same run, same evidence, months later.
  • Downstream stages should read the contract from one canonical location, not paraphrase it forward.
  • Anti-pattern avoided: agents acting on unlogged instructions no reviewer can retrieve.

In this repo: prepare calls gh issue view and uploads issue.md as an artifact; every downstream job reads that artifact, so the labeled issue is the single source of truth.

References: Workflow — plan-implement.yml · Learn — Inputs, outputs, and success criteria

The issue is the stable, human-authored task contract. prepare captures it once as issue.md, and downstream jobs reuse that same canonical input.

Good practice #2: fan-out / fan-in for planning

  • When analyses are independent, run them in parallel — don't serialize what doesn't have to be sequential.
  • Give each parallel agent its own output slot so they can't overwrite each other or race on shared state.
  • Join with a separate, deterministic merge step (not another LLM call) so the join is auditable and cheap to re-run.
  • This is the exam-tested fan-out / fan-in shape for "analyze → decide → act" pipelines.

In this repo: spec_analyzer and risk_reviewer both needs: prepare and write to different artifacts (spec, risk); plan_merger then needs: [spec_analyzer, risk_reviewer] and produces plan.json deterministically.

References: Workflow — plan-implement.yml · Learn — Agent orchestration in GitHub workflows

Independent analyses run in parallel, write separate artifacts, and join in deterministic code. This avoids unnecessary serialization and shared-state collisions.

Good practice #3: inspectable, structured plans

  • Force the plan into a fixed schema (goal, scope, steps, risks, rollback) so intent is machine-readable, not buried in prose.
  • Validate before you trust — schema-check the model's output before letting anything downstream act on it.
  • Structured plans are the substrate every governance control builds on: risk gating, required-section checks, and after-the-fact audits all read the same fields.
  • Anti-pattern avoided: "trust me" PRs where intent lives only in the diff and the review comment.

In this repo: spec_analyzer emits JSON with a fixed schema, jq validates it, and open-agent-pr renders it into the PR body using plan-template.md.

References: Workflow — plan-implement.yml · Learn — Pull request governance controls

A fixed schema turns intent into data that later controls can validate and render. The model's output is not trusted until jq parses it successfully.

Good practice #4: risk-based autonomy

Press ↓ for details

  • Not every action deserves the same level of trust — let risk drive how much autonomy an agent gets.
  • Risk must be a machine-readable signal (e.g. low | medium | high) so routing can be enforced by the platform, not by an agent choosing to be cautious.
  • Default to caution: unknown, malformed, or missing risk should be treated as high risk.
  • Low-risk work flows automatically; higher risk gets a human before it merges. Friction ends up where it matters.

In this repo: plan_merger normalizes risk, defaults to high on anything unexpected, and the two implementer jobs branch on it:

implement: needs: plan_merger environment: approval-required if: ${{ needs.plan_merger.outputs.risk != 'low' }} implement_auto: needs: plan_merger if: ${{ needs.plan_merger.outputs.risk == 'low' }}

References: Workflow — plan-implement.yml · Learn — Define risk-based autonomy

Risk is a machine-readable routing signal. plan_merger normalizes it and defaults unexpected values to high, then GitHub Actions selects either automatic implementation or the approval-gated job.

Good practice #5: approval gates through the platform

  • Human-in-the-loop should be enforced by the platform, not by an agent's good manners.
  • Reuse the same gating mechanism you already trust for deployments and protected secrets — don't invent an agent-only approval story.
  • Placing the gate on the implementation stage (not on planning) keeps thinking cheap and acting supervised.
  • Combined with a risk gate, this puts humans only where the risk warrants it — low-risk work still moves without friction.

In this repo: the implement job runs under environment: approval-required, which blocks it in the GitHub Environments UI until a reviewer approves.

References: Workflow — plan-implement.yml · Learn — Reliable workflows

The approval gate is enforced by GitHub Environments, not by agent behavior. It is placed on implementation so planning remains cheap while action is supervised where risk requires it.

Good practice #6: least privilege, per job

  • Default to no permissions. Every scope has to be granted explicitly.
  • Grant write scopes only to the specific job that needs them, and only at the stage where it needs them.
  • "Think" agents get read-only tokens; "act" agents get write tokens — and only after approval.
  • Anti-pattern avoided: a single over-scoped workflow token that lets any step do anything a compromised prompt asks for.

In this repo: the workflow header sets permissions: {}; planning jobs get contents: read + copilot-requests: write; implement jobs add contents: write + pull-requests: write.

References: Workflow — plan-implement.yml · Learn — Governance, guardrails, and operations (summary)

The workflow starts with no permissions and grants each job only what it needs. Planning jobs can inspect and call Copilot but cannot push; write capabilities arrive at implementation.

Good practice #7: layered prompt-injection defenses

Untrusted user content is a real attack surface. Assume any single layer will be bypassed and stack three:

  • Structural separation — mark untrusted content clearly (e.g. <ISSUE> tags) and tell the model to ignore directives inside.
  • Tool allowlists — give planning agents read-only capabilities so a successful injection can't exfiltrate or write.
  • Output schema validation — re-parse the model's output against a known schema before trusting it downstream.
  • Together, these make a single successful injection insufficient to cause harm.

In this repo: copilot-json-task wraps the issue body in <ISSUE> tags, restricts Copilot to --available-tools='view,glob,grep', and re-parses the JSON slice with jq.

References: Workflow — plan-implement.yml · Learn — Implement prompt injection defenses

No single prompt-injection defense is assumed sufficient. Structural separation, read-only tools, and output validation are stacked so that one successful bypass is not enough to cause harm.

Good practice #8: bounded changeset (contributor model)

Treat every agent contribution the way you'd treat a junior contributor's PR. Each change should be:

  • Understandable — the intent is stated up front.
  • Bounded — scoped to one linkable task.
  • Reviewable — opens as a draft PR so review can begin before implementation lands.
  • Policy-compliant — passes the same required checks as any human PR.
  • Reconstructable — the branch, commits, and artifacts can be replayed from the task contract.
  • Race-free — concurrency is scoped so two runs for the same task can't fight over the same branch.

In this repo: open-agent-pr opens a draft PR on agent-plan/issue-<n>-<run_id>, and a concurrency group keyed on the issue number with cancel-in-progress: false prevents races.

References: Workflow — plan-implement.yml · Learn — Apply the contributor model to agent-generated work

Treat the agent as a contributor. The change is attached to one issue, opens as a draft PR, follows repository policy, can be reconstructed, and cannot race another run for the same issue.

Good practice #9: turn the plan template into an enforced check

Press ↓ for details

  • A PR template is a suggestion; a required status check is a contract.
  • Promote plan sections (Goal, Scope, Steps, Success criteria, Risks, Rollback, Evidence, Review checklist) to a required check so they can't be silently dropped.
  • Treat the PR body as data, never as executable string — a crafted body must not be able to run code in CI.
  • Anti-pattern avoided: template drift where later PRs quietly lose the audit fields the earlier ones had.

In this repo: plan-gate.yml runs on every PR to main, reads PR_BODY as an env var, and fails if any required section is missing.

References: Workflow — plan-implement.yml · Learn — Pull request governance controls

A template only suggests structure; a status check enforces it. The PR body is handled as data, and the workflow checks that all required plan sections are present.

Good practice #10: audit trail by construction

Design the pipeline so the evidence you'd need after an incident exists automatically, not as a follow-up chore:

  • One artifact per stage, so you can replay each agent's inputs and outputs.
  • A stable link from the PR back to the workflow run that produced it.
  • The changeset anchored to the task before any code is written (e.g. an initial empty commit).
  • Every mandated check recorded on the PR itself.
  • When something regresses later, the post-mortem is about the system, not the agent.

In this repo: each stage uploads its artifact (issue, spec, risk, plan); open-agent-pr seeds the branch with a chore: start agent plan for issue #N commit; implement-agent-plan adds the implementer commit; the Plan Gate check is recorded on the PR.

References: Workflow — plan-implement.yml · Repo doc — agent-orchestration.md

The evidence needed after an incident should already exist: stage artifacts, a run link, task-anchored commits, and checks recorded on the pull request.

When would we pick a different pattern?

  • Handoff — if we didn't know upfront whether the issue needed a spec_analyzer at all (e.g. some issues are documentation-only). We'd let a triage agent decide who to transfer control to.
  • Group chat — if planning benefited from a maker/checker debate rather than one pass of "analyze + rate."
  • Magentic — if the goal itself wasn't known ("investigate this outage") and a manager needed to build a ledger of subgoals dynamically.
  • Rule of thumb: use sequential when order is fixed, concurrent when work is independent, and only reach for group-chat / handoff / Magentic when the extra flexibility earns its complexity.

Reference: Learn — Agent orchestration patterns

Use handoff for dynamic routing, group chat for productive debate, and Magentic for open-ended goals. Prefer sequential and concurrent patterns when the work shape is already known.

Closing the loop: /chronicle

Press ↓ for the demo

  • Orchestration gives you artifacts per run. Chronicle gives you evidence across sessions — every prompt, response, tool call, and modified file, indexed and queryable.
  • Local by default: session records in ~/.copilot/session-state/, a SQLite index in ~/.copilot/session-store.db.
  • Optional sync pulls sessions from CLI, VS Code, JetBrains, the cloud agent, code review and the Copilot app into one view on github.com.
  • The point for this workshop: it turns "prompt better" into feedback on your own habits, and writes the fix back into .github/copilot-instructions.md.

Reference: Changelog — Insights across your agent sessions (GA, June 2026)

Takeaways

  • Orchestration is a workflow with state, branching, and error handling — not a chain of prompts.
  • Pick the pattern that matches the shape of the work: sequential outer, concurrent inner is a durable default for "analyze → decide → act."
  • Enforce the six-item accountability checklist through the platform (GitHub) — templates, required checks, environments, permissions — not through hope.
  • Agents change who performs work; humans still own the outcome.
Close with the four takeaways from the issue notes: orchestration is a workflow, choose patterns that match the work, enforce accountability through the platform, and keep human ownership.
